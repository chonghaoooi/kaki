# kaki API

The local app has a real HTTP API and SQLite persistence. It is a development application with fictional students, not a public student service. Node 24's built-in `node:sqlite`, `http`, `crypto` and `fetch` are used; the API adds no packages.

`createApi({ dbPath, demoMode: true })` in `api.mjs` returns `{ handle(req, res), close() }`. Await `handle` before passing unhandled requests to Vite or a static server. An unhandled request returns `false`; `/api/` requests always return `true`. The application runner is [`start.mjs`](start.mjs) in this folder. Run npm commands from the repository root; see the [setup instructions](../README.md).

The production build runs `scripts/compress-client.mjs` after the protected Sites preparation step. It creates smaller Brotli and gzip sidecars for text assets using bounded build-time concurrency. The production server negotiates these using `Accept-Encoding` quality preferences, sends `Vary: Accept-Encoding`, preserves the original MIME type, and returns bodyless HEAD responses with the correct representation length. Generated files with Vite hashes use one-year immutable caching, named images use one-day caching, and HTML uses `no-cache`. Compressed sidecars older than their source are ignored; the build reports current compression sizes.

## Working behaviour

- SQLite stores profiles, sessions, one-time codes, activities, circle membership, connections, messages, private reflections, reports, blocks, tutoring requests, and Telegram consent. Foreign network object IDs are rejected before use, including IDs submitted directly to endpoints.
- Network identity comes from the authenticated account. Clients cannot edit institution, education network, age band, verification status, or email through the profile endpoint. Created activities inherit the authenticated network and require a location ID from its campus-space list. Public and nested profile responses use an explicit field allowlist, so future private database fields are not accidentally exposed.
- Sessions use random 256-bit tokens; only their SHA-256 hashes are stored. Cookies are HttpOnly and SameSite=Lax, and Secure when the socket uses TLS. Unsafe requests require an exact matching Origin. Session rotation occurs at login, logout revokes the token, and sessions expire after seven days.
- OTPs have six random digits, are stored as salted hashes, expire after ten minutes, allow five attempts, and cannot be reused. Resends wait 60 seconds. Per-address and per-IP code limits plus message and action limits are persisted in SQLite. Demo mode returns the code in the API response and sends no email.
- An activity join is transactional, idempotent, and capacity checked. Saved activities toggle. Circle joins are idempotent. Tutoring requests appear in the tutor's private incoming inbox and the requester's outgoing list. Only the tutor can accept/decline a pending request; only the requester can cancel a pending request. Duplicate identical pending submissions reuse the original request, repeated transitions to the same status are idempotent, and conflicting final transitions return 409. No payment is implied or processed.
- Messages require a mutual connection. Blocking either way prevents messages, contact consent, discovery, and member exposure. Blocking also revokes both parties' Telegram consent; unblocking does not restore external-contact consent. Private contact details are not included in public profile projections. Basic contact/address patterns are rejected in public content and messages.
- Under-18 signup defaults to undiscoverable profiles, invitations off, and membership visible to connections. Profile discovery, activity hosting, circles, tutoring, and messages respect age-band boundaries when either student is under 18. Exact age is never collected. External contact consent is unavailable for under-18 accounts.
- Activity membership privacy is applied server-side. Attendance totals remain aggregate counts; the returned participant IDs and member profiles respect community/connections/private settings. Hosts remain identifiable as activity authors.
- Reflections are visible only to their author and are never added to public profiles or recommendation scores. Journey counts describe joined activities; they are not wellbeing measurements or claims of attendance.

## Data and demo conventions

A fresh demo database contains 89 activities and 21 fictional profiles per education network, including 42 activities shared in Neighbourhood. Each network has its own Jamie account, four circles, two original discoverable tutors, a reciprocal connection waiting from Jia Wei, and a seeded conversation. Jamie also offers free peer support in their first subject and has a fictional incoming request from Jia Wei for 16 September 2026 at 3 PM. Accepting or declining that request is preserved across restarts. Demo accounts are shared within the local database; seeded circles have illustrative aggregate member counts, and only their sample members have profiles.

Original activity, mentor and tutoring records retain dates around the fixed **13 September 2026** Singapore seed anchor. The additive catalogue separately adds 54 activities per network over the 21 days after its first migration, recording that migration's current Singapore date once. Support groups likewise receive their dates when first seeded. Ordinary restarts do not move any of these dates. Discovery and mentor statistics use the current clock, so visible counts and session status change as time passes. See [demo data and retention](demo-seed.md).

Categories are `study`, `sports`, `games`, `lunch`, `interests`, and `events`; creation also supports `workshop` and `other`. `participantCount` is authoritative for capacity because privacy controls can hide participant identities. All status-changing responses include `ok: true`, with the affected object where appropriate. Errors use `{ error: string }` and an HTTP error code.

Public directory: `GET /api/institutions?network=...&q=...` returns `{institutions,source,demoMode}`. Institutions have `{id,name,network,domains,verificationMode}`. After login, `GET /api/locations` returns `{locations}`; each location has `{id,name,institutionId,network,type,public}`. Locations are curated *types of campus meeting spaces*, not verified venue bookings or permissions to enter a campus.

`GET /api/state` includes `requests` (outgoing) and `incomingRequests` (for the tutor). Requests contain `id`, `tutorId`, `requesterId`, `recipientId`, `personId` (the tutor), `date`, `time`, `message`, `status`, `createdAt`, and optional `updatedAt`. Incoming entries add a public `requester` profile; no email, privacy settings, or private reflections are disclosed. `PATCH /api/tutor-requests/:id` accepts `{status: 'accepted' | 'declined' | 'cancelled'}` and returns `{ok:true,request}`. Both listing and mutations recheck network, age band, block status, and participant identity. Blocked requests disappear from both participants' lists while the block remains.

The school directory is the Ministry of Education's complete 2026 snapshot: 147 secondary-stage entries and 22 JC/MI-stage entries, including integrated schools represented separately at each stage. It stores only school name, school website, and education level. Full-time enrolment and school ownership cannot be inferred from a shared school-email suffix, so secondary/JC entries use explicit `.kaki.test` demo domains. They are unavailable in live mode until institution SSO is integrated. There are also all five polytechnics and six autonomous universities.

## Deployment boundaries

This is ready to demonstrate locally. A student pilot still needs operational services and validation:

1. With `demoMode: false`, use a fresh, separate database. A database cannot mix demo and live modes, including legacy demo databases that lack the newer mode marker. Demo sign-in is disabled and fictional seed records are not created.
2. `RESEND_API_KEY` and `MAIL_FROM` enable real code delivery in live mode for configured exact student-email domains. Without a provider, verification fails closed. SMU and SUSS remain demo-only until their student-specific domains are verified. School SSO is required for secondary/JC. Email ownership alone does not establish current enrolment: NUS explicitly provides lifelong email. Real email-verified accounts return `verified: false`, `emailVerified: true`, `enrolmentVerified: false`, and `verificationMethod: 'email'`. A production service must integrate authoritative enrolment checks and periodic re-verification; the UI must not label these accounts verified current students.
3. Age bands are self-declared and untrusted for authoritative eligibility; `ageVerified` remains false. An adult could self-declare under 18 at initial registration. The application has age-band authorization safeguards, but has not established a user's real age. Authoritative school/age eligibility checks, guardian/school workflows where needed, and safeguarding operations are not implemented. This is not ready for an unsupervised minor-student launch.
4. Reports are stored for review; there is no live moderation team or moderator console. Contact filtering is a baseline pattern check, not comprehensive abuse moderation. No automated response or fake recipient reply is generated.
5. Telegram linking and notifications are unavailable. Consent preferences can be stored for mutually connected adults, but no usernames or Telegram messages are ever exposed or sent. A future integration must enforce both consent and network authorization again at dispatch.
6. Photos are fixed demo assets. Photo upload/storage/scanning, payments, automatic calendar integration, push notifications, account recovery, deletion/retention tooling, backups, and production monitoring are not implemented. Tutor acceptance updates the shared request status; it does not take payment, reserve a venue, or bypass mutual messaging consent.
7. The development runner only binds demo mode to loopback. Live startup requires explicit `--port`/`PORT` and `KAKI_ORIGIN` (the canonical scheme, host, and port). The API rejects unknown hosts and mismatching Origin headers; it does not trust forwarded headers. For a public service, configure TLS correctly, persistence/backups, and a process manager. The API's synchronous SQLite design is suitable for this single-process local application, not a horizontally scaled deployment.
8. `request-guard.mjs` permits only the app entrypoints and frontend asset paths. Both development and static runners deny database/WAL/SHM files, server source, environment files, hidden configuration, encoded filesystem URLs, and path traversal before passing a request to Vite or the static server. Vite also has filesystem deny rules as a second boundary. No database or credentials should ever be placed in public assets or client source.

## Verification

Run `npm run build` then `npm test`. The suite has 49 groups: 8 pure discovery/date/search groups, 5 catalogue generation/migration groups and 36 API/runner groups. The API/runner groups use real loopback HTTP requests, separate cookies, in-memory or temporary SQLite databases, and injected clocks. They cover all network pairs and object types, session/origin/host tampering, OTP domain/guess/replay/expiry rules, live provider failure, capacity/idempotency, block-aware messaging, private reflection access, future private profile fields, avatar restrictions, email-versus-enrolment verification flags, the complete directory, persistence across API instances, tutor lifecycle, neighbourhood visibility, and support-group privacy and participation. Runner tests start both development and production servers and verify that direct and encoded secret-file paths return 403 while permitted frontend endpoints continue to work. Compression tests verify Brotli/gzip/identity responses, quality preferences, cache headers, and HEAD without a body; the built-asset check is skipped if a build has not yet created compressed files.

## Support groups

Support routes require authentication and enforce the exact education network and age band. A blocked linked host makes their group unavailable. Support memberships and listener applications are private records, excluded from `/api/state`, public profiles, ordinary clubs and activity histories.

- `GET /api/support/groups` returns visible groups and the current user's listener application. `GET /api/support/groups/:id` returns one group with capacity, `myMembership`, `isHost`, and `isEnded`.
- `POST /api/support/groups/:id/join` requires `{acceptGuidelines: true, waitlist: boolean}`. Ordinary groups create `joined` membership. A one-to-one slot creates a `requested` membership and reserves capacity without confirming an appointment. A full group requires explicit `waitlist: true`. A waitlisted student can claim a released place. Transactions enforce capacity and repeat requests are idempotent. Hosts cannot take their own places; ended sessions reject new participation.
- `DELETE /api/support/groups/:id/membership` cancels a place, request or waitlist entry. It releases reserved capacity and removes chat access. Existing posted messages remain visible to group members.
- `GET` and `POST /api/support/groups/:id/messages` require joined membership, or the linked host of an ordinary group. Pending requests and waitlists do not grant access. Posts accept `{text}` with a 1,200-character limit. Responses contain an explicit message-field allowlist and filter blocked authors. The client provides manual refresh; there are no automatic replies or push notifications.
- `GET`, `POST`, and `DELETE /api/support/listener-application` read, submit and withdraw only the current user's application. Submission validates topics, formats, availability, experience and `acceptBoundaries: true`; status remains `pending`. Applications never grant host privileges or verified credentials.
- Existing reports accept visible support-group IDs and stay private. No staffed review or moderation console is connected.

The idempotent `support-groups-demo-v1` migration adds eight fictional spaces per exact demo cohort without resetting existing data or sessions. Professional hosts are explicitly fictional and unverified; listed sessions do not reserve venues or supply live meeting links. Live mode does not seed these records. Real professional verification, review/placement operations, facilitator management and appointment confirmation are outside this demo.
